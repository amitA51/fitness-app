# Sparkos Fitness — competitive research & gap inventory
2026-09-28 · read-only pass over `C:\Users\amit0\Desktop\fitness-app` · no code changed

**Headline:** the set-logging layer is already at parity with Hevy. The gaps are (a) a
progression engine that exists in full but is wired to nothing, (b) notifications that
cannot fire at all in the Android build, and (c) no home-screen surface. Items 1–3 below
are the whole story; 4–12 are real but smaller.

Sources reached are linked inline. Sources I could not reach are listed at the bottom.

---

## Top 12 opportunities
Ranked by user value × feasibility in *this* codebase.

### 1. Wire the existing progression engine into the workout — value: very high, size: S
| | |
|---|---|
| **Leaders** | Every top-ranked progression system gives a concrete *next target*, not just history. "Showing last week's performance is useful. It is not the same as making a progression recommendation." Stronglifts: complete the work → add weight; fail → repeat; fail repeatedly → deload. ([Alpha Progression, Aug 2026](https://alphaprogression.com/en/blog/best-workout-progression-system) — vendor-authored, discloses its own bias) |
| **This app** | `src/services/progressionService.ts` is 20 KB of exactly that: `calculateProgression` (`:219`) emits `recommendation` + `suggestedWeight` + `suggestedReps`, with `DELOAD` as a first-class outcome (`:19`), a 60 % deload floor (`:65`), recovery-driven deload at score < 45 (`:71-73`) and fatigue-driven at > 55 (`:74-76`), plus `calculateRPEDelta` (`:188`). Tested: `src/services/__tests__/progressionService.test.ts`. |
| **Gap** | **It is dead code.** `calculateAllExercisesProgression` (`:546`) has zero callers. The only non-test importer is `src/components/workout/ProgressionRecommendation.tsx:12`, and that component is itself never imported anywhere in `src/`. Verified two ways: grep for `from '.*progressionService'` → 2 hits (the component + its test); grep for `ProgressionRecommendation` across the repo → only self-references. |
| **Risk** | Low technical risk, real product risk: the engine has never been seen by a user, so its numbers are unvalidated in the field. Surface it as a suggestion chip next to the weight input (tap to accept) rather than as an auto-filled value, so a bad suggestion costs a glance, not a bad set. |

### 2. Notifications are structurally impossible in the Android build — value: very high, size: S
| | |
|---|---|
| **Leaders** | Hevy's rest timer "notifies you it's time for the next set" when it hits zero, and Live PR fires on a new record ([Hevy rest timer](https://www.hevyapp.com/features/workout-rest-timer/)). |
| **This app** | The web side is well built: `showRestEndNotification` routes through the service worker with `tag: 'rest-end'` + `renotify`, and only fires while the document is hidden (`src/services/notificationService.ts:97-122`), with `closeRestEndNotification` (`:130`) on return. PR notifications fire from `src/services/prService.ts:323-326`. |
| **Gap** | `android/app/src/main/AndroidManifest.xml:43` declares **only `INTERNET`**. `POST_NOTIFICATIONS` has been mandatory since API 33 and `android/variables.gradle:4` sets `targetSdkVersion = 36`. Every notification the app can produce will be silently dropped in the Play closed test. There is also no `@capacitor/local-notifications` in `package.json:31-34` (only `core`, `cli`, `android`), so nothing can fire while the WebView is not running. |
| **Risk** | The permission itself is one manifest line plus a runtime request. Do not bundle it with the scheduler work in item 3 — ship the permission first so the *existing* rest-end and PR notifications start working for the 12 testers. |

### 3. No local reminder scheduler — the reminder toggle is a placebo — value: high, size: M
| | |
|---|---|
| **Leaders** | Hevy's day-of-week routine widget lets you schedule workouts per weekday and start today's from the home screen ([Hevy widgets FAQ](https://www.hevyapp.com/features/home-screen-widgets/)). |
| **This app** | `NotificationConfig` already models the whole thing: `workoutReminderTime`, `workoutReminderDays`, `missedWorkoutAlertDays`, `nutritionReminderTimes` (`src/services/notificationService.ts:5-12`). |
| **Gap** | `showWorkoutReminder` (`:144`) and `showNutritionReminder` (`:165`) have **zero callers** — verified by grep across `src/`. The only thing the "תזכורת אימון" toggle gates is `checkMissedWorkouts`, called once at boot from `src/main.tsx:140`. So the user is told "you haven't trained in 3 days" only at the moment they open the app — i.e. exactly when the reminder is useless. `src/pages/settings/sections/NotificationsSection.tsx:34-35` admits this in a comment ("no scheduler exists, so it did nothing"). There is also no UI anywhere to set the reminder *time*, and the two defaults disagree: `08:00` in `notificationService.ts:16` vs `18:00` in `src/contexts/SettingsContext.tsx:71`. |
| **Risk** | Needs `@capacitor/local-notifications` (native, pinned version) + item 2's permission. Android 14+ also restricts exact alarms — use inexact daily repeats, which is correct for a reminder anyway. |

### 4. Android home-screen widget — value: high, size: L
See the dedicated spec below. Nothing exists: no `receiver` or `appwidget-provider` in the manifest, no Kotlin beyond `MainActivity`.

### 5. Equipment-aware loading — value: high, size: S
| | |
|---|---|
| **Leaders** | "A theoretically perfect load is irrelevant if the equipment does not allow you to use it." Alpha Progression, MacroFactor and Gravl all store the weights actually available and progress reps instead of forcing an impossible jump ([source](https://alphaprogression.com/en/blog/best-workout-progression-system)). |
| **This app** | `src/utils/plateCalculator.ts:9-12` **already accepts** `barWeight` and `availablePlates`, and it is tested with a reduced set (`src/utils/__tests__/plateCalculator.test.ts:19`). |
| **Gap** | Nothing ever passes them. `src/components/workout/overlays/PlateCalculatorOverlay.tsx:23` hardcodes `PLATES_KG = [25, 20, 15, 10, 5, 2.5, 1.25]`, and `progressionService.ts:62-63` hardcodes `2.5` / `5` kg increments. A trainee whose gym tops out at 20 kg dumbbells gets arithmetic, not advice. |
| **Risk** | Low. One settings screen (bar weight + plate checkboxes + dumbbell ladder) feeding both call sites. Scope creep risk: resist per-gym profiles for v1. |

### 6. Rest timer: per-exercise value is template-only — value: medium, size: S
Hevy lets you tap the timer mid-workout and change it **for that exercise**, 5 s to 5 min, with a global default under Settings › Workouts › Default Rest Timer ([source](https://www.hevyapp.com/features/workout-rest-timer/)).
This app has the global auto-start (`useWorkoutSettings.ts:258`, `useAutoStartRest` `:568`), ±15 s on the live ring (`InlineRestTimer.tsx:346`, `handleAddRestTime` in `useWorkoutHandlers.ts:284`), and per-exercise `restSeconds` baked into templates and the program (`types/index.ts:65,131`, `bbtProgram.generated.ts:73`, `ExerciseCard.tsx:81`). Missing: changing this exercise's rest for the rest of the session without editing the template. Risk: none.

### 7. Rest-timer ongoing notification / Live Activity — value: medium, size: L
Hevy ships this on Android — a lock-screen surface showing rest timer, current exercise, next set and target reps (help-centre article, snippet only — see unreached sources). This app's rest-end notification is a single fire-and-forget alert; there is no persistent surface while resting with the screen off. Needs a foreground service. Risk: Play policy scrutiny on foreground-service types; genuinely L.

### 8. Sets per muscle group per week — value: medium, size: S
Hevy ships "Sets Per Muscle Group Per Week" and a muscle-distribution chart as distinct features ([feature list](https://www.hevyapp.com/features/)). This app has the muscle map (`src/components/fitness/MuscleMap.tsx`) and weekly distribution by **volume** (`src/components/insights/MuscleDistribution.tsx:28` `computeWeeklyMuscles`, `src/services/analytics/volumeMetrics.ts:174` `computeMuscleVolumes`, `trainingLoadService.ts:183` `addMuscleVolume`). Gap: hypertrophy audiences reason in *sets*, not kg·reps. Same data, different reducer. Risk: none.

### 9. Monthly report / year in review — value: medium, size: M
Hevy ships both ([feature list](https://www.hevyapp.com/features/)). This app has a weekly text report for sharing (`src/pages/settings/sections/WeeklyReportSection.tsx:18` `generateWeeklyReport`) and a share card (`src/utils/workoutShareCard.ts`, used at `WorkoutSummary.tsx:30`). Grep for `monthlyReport|yearInReview|weeklyRecap` across `src/` → zero hits. Gap: no period rollup beyond a week. Risk: an empty-state month for a new tester is the main failure mode.

### 10. Per-working-set targets — value: medium, size: M
The strongest systems differ target-by-set because fatigue accumulates within an exercise ([source](https://alphaprogression.com/en/blog/best-workout-progression-system)). This app's ghost/previous values are per-set (`usePreviousSetData.ts:33`, rendered as `ghostValue` at `ExerciseDisplay.tsx:823,836`) — good — but `progressionService` returns one `suggestedWeight` per exercise (`:32`). Do item 1 first; this is its follow-up.

### 11. Reminder-time UI + a single source of truth for defaults — value: medium, size: S
Covered in item 3's evidence: the config field exists, no screen writes it, and the two defaults disagree (`08:00` vs `18:00`). Worth fixing in the same change as item 3, not before.

### 12. Deload as a visible plan event, not just a per-exercise verdict — value: medium, size: M
Alpha Progression, MacroFactor and RP put deloads in the *calendar* as a scheduled reduction in stress; Stronglifts triggers one after N configured failures ([source](https://alphaprogression.com/en/blog/best-workout-progression-system)). This app computes `DELOAD` per exercise from recovery/fatigue (`progressionService.ts:19,71-76`) but has no program-level deload week. `src/services/programProgressService.ts` + `restDays.ts` are the natural hosts. Risk: this is programming opinion, not plumbing — get the coach to sign off on the rule before building it.

## Android widget spec

**Why a widget at all.** Hevy's widgets are interactive, not decorative: "Tapping on a routine in a widget automatically starts it as a live workout", the aggregate widget lets you pick metric and date range, and the routine-of-the-day widget schedules per weekday ([Hevy widgets](https://www.hevyapp.com/features/home-screen-widgets/)). Android users specifically ask for the *streak* widget by name when they switch from iOS ([r/Hevy](https://www.reddit.com/r/Hevy/comments/18yczov/any_plans_for_an_android_widget/) — title/snippet reached, comment bodies not). A third-party tracker shipped "a fourth home-screen widget: today, done or not" as a headline release note ([GymMane releases](https://github.com/InlitX/GymMane/releases) — snippet).

The product principle here is "a set is logged in under 3 seconds". A widget that starts today's session removes the two taps before the first set. That is the only justification needed; the stats are secondary.

**What to show, in priority order:** ① today — rest day or session name; ② one tap that starts it; ③ streak, counting planned rest days as intact (the app already computes this, see "already better" below); ④ week grid.

| Size | Cells | Content | Tap target |
|---|---|---|---|
| **Small** | 2×1 | Today's session name (or `יום מנוחה`), streak number | Whole widget → start today's session, or open Home on a rest day |
| **Medium** | 4×2 | Above + 7-day grid mirroring `WeeklyGrid` (`src/components/dashboard/WeeklyGrid.tsx:15`) + "התחל אימון" button | Button → start; a day cell → that day's `WorkoutDetail` |
| **Large** | 4×3 | Above + top 3 exercises for today with last session's weight×reps, from `usePreviousSetData`'s data source | Each row → deep-link into the workout at that exercise |

**Constraints for whoever builds it**
- Glance/`AppWidgetProvider` in Kotlin under `android/app/src/main/`; needs a `receiver` + `appwidget-provider` XML — neither exists today.
- The widget process cannot read IndexedDB. It needs a native-side mirror. `src/services/localStateMirror.ts` is the closest existing concept — extend that pattern to write a small JSON blob to `SharedPreferences` on workout finish, rather than inventing a second sync path.
- RTL: `android:supportsRtl="true"` is already set (`AndroidManifest.xml:9`). Hebrew label + Latin number in one string must be wrapped the way the app already does it — see `<bdi dir="ltr">` at `src/components/workout/components/ExerciseCard.tsx:158`.
- Widgets update on a throttle, not live. Hevy's own FAQ only promises "update automatically when you complete workouts" — match that expectation and refresh on finish + on midnight rollover, nothing more.

## Local-notification playbook
Local only. No FCM, no server push. Everything below is schedulable with `@capacitor/local-notifications` once item 2's permission lands.

**Prerequisite, not optional:** `POST_NOTIFICATIONS` in the manifest. Without it nothing in this section runs.

| Reminder | Default | Cap | Why |
|---|---|---|---|
| Rest-end | on, fires at 0 | per set, suppressed while app is visible | Already implemented and already correct (`notificationService.ts:97-122`). Hevy notifies at zero too. |
| New PR | on | once per record | Already implemented (`prService.ts:323`). Hevy ships this as "Live PR". |
| Workout day | **off**, ask after the 3rd logged workout | 1/day, only on a scheduled training day, never on a rest day | `restDays.ts` already knows which days are rest days — use it. A reminder on a planned rest day is the single fastest way to get the whole channel muted. |
| Missed workout | off | **1 per 7 days, hard cap** | Today's `missedWorkoutAlertDays: 3` (`notificationService.ts:19`) is a reasonable trigger but there is no cap, so a lapsed user would get one every launch. |
| Nutrition meal times | off, never auto-enabled | 3/day max, only if nutrition was used in the last 7 days | The config already lists `['08:00','13:00','19:00']` (`:20`). Gate it on actual use — otherwise it is three daily pings about a feature the user ignored. |
| Weekly summary | off | 1/week, Sunday evening | Pairs with item 9. Retention value comes from *reviewing*, which is a pull; keep it opt-in. |

**Defaults:** align on `18:00` (the `SettingsContext.tsx:71` value, not the `08:00` in `notificationService.ts:16`) — an evening nudge matches a post-work gym trainee better than a morning one. Ship the time picker in the same change; a reminder the user cannot move is a reminder they will disable.

**Opt-in moment:** not at first launch. Ask immediately after the 3rd completed workout, on the summary screen, when the user has just seen value — and ask for the *reminder*, not for "notifications". One sentence, one switch, no modal.

**Copy tone (Hebrew, RTL):** the existing strings are the right register — `'זמן לאימון'` / `'האימון המתוכנן ממתין.'` (`:145`), `'לא התאמנת מזמן'` (`:150`), `'שיא אישי חדש'` (`:158`). Factual, no exclamation marks, no guilt, no streak-loss threats. Keep it. Never put a number inside a Hebrew sentence without a `bdi` wrapper — `'עברו ${daysSince} ימים'` (`:151`) is fine in a notification body because the OS handles it, but the same pattern in the UI is not.

**Global rules:** every channel individually switchable; one Android notification channel per category so the user can mute one without muting the rest; nothing fires between 22:00 and 07:00 except rest-end; total non-rest-timer notifications capped at 1/day.

## Things this app already does better — protect these

1. **The streak forgives planned rest days.** `computeStreakWithRests` (`src/utils/restDays.ts:114`) folds scheduled rest into the streak. Hevy surfaces "your weekly active streak **and the number of rest days you've had**" as two separate numbers ([Hevy widgets](https://www.hevyapp.com/features/home-screen-widgets/)) — which means a correctly-taken rest day still reads as a gap. This app's version is the honest one and it is the reason the streak here is not a gimmick. Do not "simplify" it.
2. **Rest-end notification discipline.** Fires only while the document is hidden, coalesces via `tag`, `renotify`s, and is actively closed when the user returns or skips (`notificationService.ts:97-136`). Most apps just fire and leave it.
3. **Readiness / training load is wired and free.** `calculateTrainingLoad` feeds Progress › Recovery (`src/pages/progress/useProgressData.ts:30`, `ReadinessReadingCard.tsx:34`, `RecoveryTab.tsx:8`). Recovery-aware autoregulation is what RP Hypertrophy charges $299/yr and Gravl $79/yr for ([source](https://alphaprogression.com/en/blog/best-workout-progression-system)).
4. **e1RM that explains itself and refuses to lie.** `ExerciseDetail.tsx:5` ships "a plain-language note on HOW the e1RM is derived", and the chart quantises to whole kg so a 0.2 kg wobble draws flat (`GlowAreaChart.test.tsx:124-125`). Leaders show the number; this shows the number *and* its uncertainty.
5. **One rule for what counts as volume.** Warm-up sets contribute 0, in exactly one place (`src/utils/workoutMath.ts:31`), enforced by test (`progressionService.test.ts:180`). This is "data is always trustworthy" made mechanical.
6. **Hebrew RTL and bidi are first-class, not a locale file.** `<bdi dir="ltr">` around numbers inside Hebrew strings (`ExerciseCard.tsx:158`), `dir: 'rtl', lang: 'he'` on notifications (`notificationService.ts:64-65`). None of the seven leaders ship real Hebrew. This is the moat.
7. **Offline-first without an account.** 48 KB `offlineQueue.ts` + IndexedDB. Hevy requires a login to log a set.
