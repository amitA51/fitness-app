## Worker survival protocol

These are hang and crash traps verified on **this** Windows host. Every dispatch
must carry the relevant lines inline — a worker never sees the board.

**Never leave a server running across shell calls.** On Windows the child
inherits the tool's stdout pipe, so the call blocks forever while the server
lives. Start + use + stop in ONE command:
`$p = Start-Process npm -ArgumentList 'run','preview' -PassThru; try { <checks> } finally { Stop-Process -Id $p.Id -Force }`

**Never run a watch-mode command.** `npm run test` (vitest watch), `npm run dev`
and `vitest --watch` never return. Only `npm run test:run`, or
`npx vitest run <path>` for one area.

**Playwright starts its own server — do not start one.** `playwright.config.ts`
has `webServer` on `http://localhost:4173` with `reuseExistingServer`. Vite dev
is port 3000. Therefore **only one worker per batch may run Playwright**, and no
worker may hand-start a preview/dev server alongside it.

**The `shell` tool truncates output at the first Hebrew character** (exit 0, rest
of the output silently lost). For anything that may emit Hebrew — test names,
source lines, copy — use the `read` / `grep` tools. In `shell`, pipe to an ASCII
summary: `... | Select-String -Pattern 'PASS|FAIL|Tests|error'`, or redirect to a
log file and read the log with `read`.

**Screenshots:** `npx playwright test e2e/visual-qa.spec.ts --project="Mobile Chrome (Pixel 5)"`
writes to `./visual-qa/*.png`.

**Keep the task narrow.** Observed failure mode on this host:
`AcpProcessDied: Runtime process died during prompt` — an over-wide task dies
mid-run and reports nothing. The lead therefore verifies `git status --short`
itself after every batch, so work that landed from a dead worker is still found.

**Workers never run git.** No commit, push, checkout, reset, stash, or branch.
Changes are left in the working tree. The lead owns git.

## Conflict control

Many changes are coming and some will collide. Rules, in order:

1. **The board is written before dispatch.** A task that is not on the board does
   not exist.
2. **File ownership is exclusive.** Every dispatched task declares its files in
   the `files:` line. Two `dispatched` tasks may never name the same file — if
   they must, they go in different batches.
3. **Shared-surface files are lead-serialized.** Anything global is single-owner,
   one task at a time, never in a parallel batch:
   `src/index.css`, `tailwind.config.js`, `src/App.tsx`, the router, the design
   tokens, `package.json`, `vite.config.ts`, `biome.json`.
4. **Design and dev never share a file in one batch.** A component's logic and
   its styling are the same file here — that is a serial handoff, not parallel
   work.
5. **One e2e/Playwright worker at a time** (port 4173, see above).
6. **After every batch the lead re-runs the baseline** (`git status --short` +
   `npm run verify` + `npm run test:run`) before accepting anything. A green
   worker report on a red tree is a reject.

### DECIDED 2026-08-28 — admin assignment model

Amit chose: **a hidden admin screen inside the app, visible only to his user.**

Architecture the lead fixed so two workers cannot assume different shapes:

- New table `app_admins(user_id UUID PK REFERENCES auth.users)`. **No client
  write path at all** — `authenticated` gets SELECT of its own row and nothing
  else. Chosen over a `profiles.is_admin` column because clients already UPDATE
  their own `profiles` row, so a column there needs a trigger to defend it.
- `is_app_admin()` SECURITY DEFINER helper, same style as the existing
  `is_coach_of()` / `is_client_of()`.
- `admin_set_coach(_target UUID, _business_name TEXT)` SECURITY DEFINER, first
  statement asserts `is_app_admin()` or raises. This is the ONLY promotion path.
- `become_coach()` loses `GRANT ... TO authenticated`. Not dropped — existing
  migrations and tests reference it.
- **Demotion is deliberately out of scope.** The existing guard trigger blocks
  coach→trainee while `coach_profiles` rows exist, so un-assigning would have to
  destroy a coach's business data and their trainee links. Amit did not ask for
  it. Known gap, reported to him, not built.
- Amit's own user is seeded as admin by ONE manual SQL statement he runs once —
  a migration cannot know his user id, and hardcoding it would be wrong.
