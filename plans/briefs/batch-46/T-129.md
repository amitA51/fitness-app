  `INCREASE_WEIGHT | MAINTAIN | DECREASE_WEIGHT | INCREASE_REPS | DELOAD`, `suggestedWeight`,

  `src/components/workout/ProgressionRecommendation.tsx` is imported NOWHERE. No user has ever seen it.

  'אימון קודם: 72.5 ק״ג × 8' plus a naive always-'+2.5 ק״ג' chip — the same nudge after a failed set,
  after a deload week, on a dumbbell curl.
- Increments are hardcoded (`WEIGHT_INCREMENT_SMALL = 2.5`, `_MEDIUM = 5`, ~:62-63). Catalogue exercises
  carry `equipment` ('barbell' | 'dumbbell' | 'machine' | 'cable' | bodyweight...) in
  `src/data/builtInExercises.ts`; `src/utils/plateCalculator.ts:9-12` already accepts bar + plates.
- Research (plans/RESEARCH-2026-09-28.md #1, #5): leaders give a concrete NEXT TARGET, not history; show it
  as a suggestion you tap to accept, so a bad suggestion costs a glance, not a bad set.

## Build
1. A hook, e.g. `src/components/workout/hooks/useProgressionSuggestion.ts`: for the current exercise, run
   `calculateProgression` over completed sessions (read them the way the live screen already gets
   previous-set data — find `usePreviousSetData` and reuse its source; no new slow queries; memoise per
   exercise id). Target reps/sets from the current workout exercise. Pass fatigue/recovery scores only if
   the app already computes them cheaply (see `trainingLoadService.ts`); otherwise omit.
2. Equipment-aware increments: replace the two constants with a small table keyed by equipment (barbell
   2.5, dumbbell 2 — per hand, machine/cable 5 or the machine's step, bodyweight → INCREASE_REPS, never a
   weight). Unknown equipment falls back to today's 2.5. Round suggestions to loadable values
   (barbell: multiples of 2.5 given 1.25 plates). Keep every existing progressionService test green;
   add tests per equipment and for rounding.
3. UI in the 'אימון קודם' strip: keep last time, replace the naive chip with the engine result as ONE
   compact, tappable chip: increase → '↑ 75 ק״ג', hold → '= 72.5', reps → '↑ 9 חזרות', deload/decrease →
   '↓ 60 ק״ג'. One short Hebrew reason line (from `reasons[0].message`, rewritten short if needed —
   read the hebrew-content-writer skill). Tapping fills the CURRENT set's weight/reps (the same code path
   the +/- steppers and the numpad use); it never logs a set. With < 2 sessions of history show last time
   only (no 'maintain' chip for new exercises — noise). Numbers `dir="ltr"`, tabular. Existing tokens only:
   accent for increase; for deload/decrease use an existing warning/caution token if one exists
   (grep tokens.css) — no new colours. 44px target, Hebrew aria-label describing the suggestion.
4. Dead code: either render `ProgressionRecommendation.tsx` or DELETE it (and its test) — do not leave it
   orphaned. Explain which and why.
