## [26] MEDIUM — Destructive delete-all has no error handling — a mid-loop failure aborts silently with no UI
**File:** src/pages/Settings.tsx (line ~46)
**Dimension:** error-handling
**Description:** handleDeleteAllData is `const handleDeleteAllData = async () => { await deleteAllUserData(); window.location.reload(); };` with no try/catch. deleteAllUserData loops `await dbClear(store)` over every store; if any dbClear rejects (IndexedDB locked, quota/transaction error), the await rejects, window.location.reload() never runs, and the user sees the confirm dialog close with NO feedback — some stores cleared, some not, no error state. The unhandled rejection is swallowed by React's event system.
**Proposed fix:** Wrap in try/catch: on success reload; on failure show a Hebrew error toast/inline message (e.g. 'מחיקת הנתונים נכשלה, נסה שוב') and do not reload, so the partial state is recoverable and the user is informed.
**Verifier evidence:** Confirmed by reading all files in the chain. handleDeleteAllData (src/pages/Settings.tsx:46-49) is `async () => { await deleteAllUserData(); window.location.reload(); }` with no try/catch. deleteAllUserData (src/services/settingsService.ts:49-57) loops `await dbClear(store)` sequentially over 13 stores then removes localStorage keys. dbClear (src/services/indexedDBCore.ts:296-308) genuinely rejects on tx.onerror/onabort, and initDB rejects on onerror/onblocked — so IndexedDB failures (locked DB, quota, version-change abort, blocked-by-other-tab) propagate as a rejected promise. On rejection: window.location.reload() never runs, stores are partially cleared (mid-loop), and there is NO error UI. The confirm dialog (DangerZoneSection.tsx:21-24) already called setConfirmOpen(false) before onDeleteAll(), so the user sees the dialog vanish with no feedback while data is half-deleted; the rejection becomes an unhandled promise rejection. This is a destructive, irreversible operation with zero failure feedback. Crucially, the sibling handler handleSignOut (Settings.tsx:36-44) DOES wrap its async call in try/catch + logger, establishing a project convention that handleDeleteAllData violates. Not handled anywhere downstream. The proposed fix (try/catch, Hebrew inline error, skip reload on failure) matches the codebase's RTL/Hebrew conventions and the existing handleSignOut pattern. MEDIUM severity is fair: only triggers on uncommon IndexedDB failure, but the silent partial-delete UX is a genuine defect.
